Этап: 1 · Исполнитель: Kimi/OpenCode · Главное ревью: Codex
Базовый HEAD реализации: `31531ed` · Визуальная приёмка: не требуется

## Наблюдаемый результат

Существующий симулятор загружает игровой конфиг забега I и проходит утверждённый
intended path от первого ручного Scrap до EMP за 28–35 минут.

```powershell
python tools/sim/sim.py --config Assets/Game/Resources/balance/run1.json --plan tools/sim/run1-plan.json
```

Задача проверяет темп математической модели. Она не доказывает интерес живого игрока.

## Утверждённый игровой цикл

1. Игрок вручную режет корпус и получает Scrap.
2. Рабочие режут корпус и носят Scrap на склад.
3. `salvage_rig` усиливает добычу.
4. `crew_quarters` поддерживает рост числа рабочих.
5. `workshop` улучшает инструменты и открывает авто-доставку.
6. Корабль просыпается и создаёт угрозу.
7. `guard_post` позволяет пережить угрозу и пробить внешний слой.
8. EMP завершает забег.

В симуляторе `baseOutput` здания — его нормализованный вклад в общий Scrap/sec.
Это не означает, что казарма или пост визуально «производят лом»: Unity-слой позже
покажет их собственную роль, сохранив те же экономические числа.

## run1.json — фиксированная структура

Использовать текущую схему `smoke-config.json` со следующими данными:

- `schemaVersion = 1`, `tickSeconds = 1`, `maxSeconds = 2400`;
- ручное действие: cooldown `1`, останавливается после `auto_delivery`;
- worker: `id=worker`, `costGrowth=1.17`, вехи `5→1.5`, `10→1.75`, `20→2.0`;
- четыре здания, каждое `costGrowth=2.4`, `outputGrowth=1.6`, `maxLevel=6`:
  `salvage_rig`, `crew_quarters`, `workshop`, `guard_post`;
- fixed purchases:
  `auto_delivery`, `tool_boost`, `ship_stirs`, `base_expands`,
  `first_threat`, `hull_breach`, `emp`;
- только `emp` имеет `endsRun=true`;
- категории fixed purchases:
  `auto_delivery=mechanical`, `tool_boost=mechanical`, `ship_stirs=visual`,
  `base_expands=visual`, `first_threat=mechanical`, `hull_breach=mechanical`,
  `emp=mechanical`.

Добавить одно необязательное поле верхнего уровня:

```json
"prestigeMultiplier": 1.0
```

В smoke-конфиге отсутствие поля означает `1.0`; менять smoke JSON нельзя.

Исполнитель **подбирает только**:

- `manualAction.yield`;
- worker `baseCost` и `baseRate`;
- у зданий `baseCost` и `baseOutput`;
- стоимости fixed purchases;
- `prestigeMultiplier`.

Нельзя менять формулы, growth, вехи, порядок плана или целевые окна ради зелёного теста.
Все числа конечные и положительные; внутренние расчёты не округлять.

## Минимальное расширение симулятора

1. `Config` получает `prestige_multiplier: float = 1.0`.
2. `simulate()` получает keyword-only параметры `income_scale=1.0` и
   `production_multiplier=1.0`. Их произведение умножает manual и passive income,
   но не цены. Оба значения строго положительные.
3. CLI:
   - `--income-scale N`, default `1.0`;
   - `--prestige` — использует `config.prestigeMultiplier` как production multiplier.
4. Summary дополнительно печатает `maxMeaningfulGapSeconds=N`.
5. Meaningful event — категория `unlock`, `visual` или `mechanical`.
   Максимальный gap считается от `t=0` до первого meaningful event и между такими
   событиями до EMP. `routine` gap не закрывает.

Не добавлять оптимизатор. Числа настраиваются в JSON, код остаётся общим.

## Целевые окна baseline (`income-scale=1.0`)

Границы включительные, кроме явно указанного `<`.

| Событие | Цель, сек |
|---|---:|
| worker count 1 | 20–44 |
| `salvage_rig` L1 | 90–120 |
| `crew_quarters` L1 | 210–270 |
| `workshop` L1 | 360–420 |
| `auto_delivery` | 420–479 |
| `tool_boost` | 510–570 |
| `ship_stirs` | 900–960 |
| `base_expands` | 1050–1110 |
| `guard_post` L1 | 1260–1320 |
| `first_threat` | 1470–1530 |
| `hull_breach` | 1620–1740 |
| `emp` | 1680–2100 |
| максимальный meaningful gap | `< 480` |

Sensitivity не обязана попадать в эти окна, но обязана быть монотонной:
`EMP(0.9) > EMP(1.0) > EMP(1.1)`.

Prestige-прогон использует тот же план и `prestigeMultiplier` из JSON. Его EMP:
`240–360` секунд. Это бюджет D-003, а не обещание готового престижа.
