# Рабочий процесс

Цель процесса — быстрее получать проверяемую игру, а не отчёты агентов.

## Роли

| Кто | Ответственность |
|---|---|
| Кларус | направление, спорные решения, визуальная приёмка |
| DeepSeek Pro/OpenCode | реализация задачи, тесты, запуск проверок |
| Codex | архитектура, постановка задач, главный code review, документация |
| Claude | независимая критика на гейтах этапов или по запросу |
| Kimi `@reviewer` | необязательный быстрый pre-review внутри OpenCode |

Claude имеет доступ к проекту, но не меняет спеки, код или Git без отдельной просьбы
владельца. Его обычный результат — `docs/reviews/<ID>/claude.md`.

## Цикл задачи

1. Codex или владелец формулирует `docs/tasks/<ID>.md`: один наблюдаемый результат,
   конкретные проверки и список запретов.
2. DeepSeek Pro проверяет задачу на противоречия. Если их нет — реализует и запускает тесты.
   Коммит не делает.
3. Codex читает фактический diff и тесты. Отчёт исполнителя — только подсказка.
4. Codex пишет `docs/reviews/<ID>/codex.md` с вердиктом:
   - `ACCEPT` — критерии выполнены;
   - `FIX` — перечислены обязательные дефекты со сценарием отказа;
   - `STOP` — нужно решение владельца.
5. После `FIX` исполнитель исправляет только перечисленное, затем Codex проверяет снова.
6. Владелец принимает то, что видно только глазами, по свежей сборке или Play mode.
7. После `ACCEPT` Codex сразу коммитит и пушит принятую задачу. Для остальных агентов
   коммит и push — только по явной команде владельца.

Claude обязателен только перед закрытием этапа и при спорном архитектурном решении.
Для обычной маленькой задачи отдельные ревью DeepSeek и Claude не нужны.

## Что проверяет главное ревью

Порядок важен:

1. задача выполнима и не противоречит контракту/этапу;
2. тесты упадут при сломанной реализации;
3. diff реализует все критерии и не делает лишнего;
4. нет балансовых чисел в коде, `UnityEngine` в Core и будущих абстракций;
5. команды проверки действительно запускались;
6. визуальное явно оставлено владельцу, если оно требуется.

Находка должна содержать файл/строку, конкретный вход или состояние и неверный
результат. Советы по стилю без риска не блокируют задачу.

## Git и параллельная работа

- Локальный источник правды: `O:\AI\GREAT-IDLE-GAME`.
- GitHub: `Rainbow888888/GREAT-IDLE-GAME`, ветка `main`.
- Перед правкой: `git status`. При чужом незакоммиченном diff — не перезаписывать его.
- Агент меняет только названные в задаче файлы.
- Добавление в индекс — поимённо; `git add -A` запрещён.
- Pull выполняется только на чистом дереве.
- Codex после собственного `ACCEPT` коммитит и пушит сразу; остальные случаи требуют
  явной команды владельца.

## Передача контекста

`NEXT_CHAT.md` — короткий проверенный снимок, а не вторая спецификация. После рабочего
коммита в нём обновляются: HEAD/синхронизация, текущий этап, следующий результат,
критерии и один стартовый промпт. История решений остаётся в `docs/DECISION_LOG.md`.
